💡 DB 초보자를 위한 덤프 & WAL 로그 완벽 가이드

"왜 조회만 했는데 로그가 생기고 DB가 무거워질까?" 완벽 해부

🔍 왜 SELECT 조회에 WAL/로그가 쌓일까?

주범: 힌트 비트(Hint Bits) / 페이지 상태 변경

DB는 데이터를 읽을 때 "이 데이터가 진짜 커밋된 최신 데이터가 맞나?"를 검증합니다. 최초로 읽는 세션이 "확인 완료!"라는 도장(Hint Bit)을 데이터 페이지에 직접 적는데, 이 도장을 찍는 것 자체가 디스크 쓰기(Write) 작업으로 간주하여 WAL 로그가 폭증하게 됩니다.

🧹 VACUUM이 하는 일 쉽게 이해하기

비유: 도배공사와 청소

책상 위에 버려진 쓰레기(Dead Tuple)를 정리하고, 나중에 들어올 손님(SELECT)이 머뭇거리지 않고 바로 읽을 수 있도록 미리 "확인 도장"을 다 찍어두는 사전 도배 작업입니다.

⚔️ 일반 VACUUM vs VACUUM FULL 차이점

구분 일반 VACUUM (권장) VACUUM FULL (주의)
동작 방식 기존 공간 안에서 쓰레기 표식만 남기고 도장(Hint Bit) 갱신 새 테이블을 만들어서 데이터 전체를 복사 후 교체
서비스 영향 (Lock) 안전 조회/수정/삭제 모두 정상 작동 위험 테이블이 잠김 (단순 SELECT도 불가능)
소요 시간 비교적 매우 빠름 수십~수백 배 매우 느림 (인덱스까지 재구성)
목적 덤프/조회 전 로그 폭증 방지, 공간 재활용 DELETE를 수천만 건 해서 디스크 용량을 완전히 줄여야 할 때

⚡ VACUUM 명령어 세부 가이드

테이블 지정 없이 VACUUM; 실행 시 전체 적용

동작: DB 내의 모든 테이블을 순차적으로 스캔하며 청소 및 힌트 비트를 정리합니다.

  • 장점: 테이블명을 일일이 지정할 필요가 없어 덤프 전 전체 대비용으로 매우 편리함
  • 특징: FULL이 아니므로 진행 중에도 서비스 조회가 전혀 막히지 않음
  • 주의: DB 전체를 훑으므로 작업 완료까지 총 소요 시간이 길어질 수 있음
VACUUM; -- DB 전체 대상 일반 VACUUM 실행

VACUUM vs VACUUM ANALYZE 옵션 차이

핵심 차이: 통계 수집(ANALYZE) 여부

명령어 주요 기능 추천 상황
VACUUM 페이지 청소 + Hint Bits 정리 PK 기준 명확한 슬라이싱 조회 전 (빠름)
VACUUM ANALYZE 청소 + 쿼리 통계정보 수집 복잡한 JOIN/조건절 쿼리 최적화 필요 시

* ANALYZE는 데이터 일부만 샘플링하므로 추가 소요 시간은 수 초~수십 초로 매우 적습니다.

🗄️ 데이터베이스(DB)종류별 동작 방식 & 대응법

PostgreSQL 질문자님의 DB

1. 조회 시 WAL이 쌓이는 이유

MVCC 구조상, SELECT 작업이 Hint Bits(커밋 확인 플래그)를 데이터 페이지에 직접 기록하므로 Dirty Page가 생겨 WAL이 발생합니다.

2. 해결 및 조치 방법

덤프 전 일반 VACUUM을 실행하여 힌트 비트를 미리 확정(Freezing)짓습니다.

-- 개별 테이블 VACUUM VACUUM target_table_name; -- DB 전체 VACUUM (권장) VACUUM;
MySQL (InnoDB)

1. 조회 시 Redo/Undo 로그가 쌓이는 이유

MySQL은 PostgreSQL과 달리 단순 SELECT만으로는 로그가 거의 쌓이지 않습니다. 하지만 Long-running Transaction(긴 트랜잭션)으로 덤프를 받으면 Undo Log 공간(Purge 지연)이 팽창할 수 있습니다.

2. VACUUM에 해당하는 명령어

MySQL에는 VACUUM이 없으며 OPTIMIZE TABLE이 VACUUM FULL과 유사하게 동작합니다.

-- 디스크 공간 재정렬 (락 발생 주의) OPTIMIZE TABLE target_table_name;
Oracle

1. 조회 시 Redo 로그가 쌓이는 이유

Oracle 역시 단순 조회는 Redo Log를 거의 만들지 않으나, Delayed Block Cleanout 현상(커밋 후 첫 조회 시 블록 헤더 정리)이 일어날 때 소량의 Redo 로그 및 디스크 쓰기가 발생합니다.

2. VACUUM에 해당하는 명령어

Oracle은 수동 VACUUM 대신 Segment Shrink 또는 Table Move를 사용해 조각모음을 수행합니다.

-- 조각모음 및 공간 환수 (Row Movement 활성화 필요) ALTER TABLE target_table_name SHRINK SPACE;
Microsoft SQL Server

1. 조회 시 Transaction Log가 쌓이는 이유

SELECT 자체로 트랜잭션 로그가 치솟지는 않지만, 대용량 조회 시 메모리가 부족해 TempDB 공간을 쓰게 되면 TempDB 관련 로그가 급증할 수 있습니다.

2. VACUUM에 해당하는 명령어

인덱스 조각모음(Reorganize / Rebuild)을 통해 인덱스 및 페이지 공간을 정리합니다.

-- 서비스 중 조각모음 (일반 VACUUM과 유사) ALTER INDEX ALL ON target_table_name REORGANIZE;

📌 실무 핵심 요약

  • PostgreSQL은 구조 특성상 대용량 덤프/조회 전 일반 VACUUM 실행이 필수적입니다.
  • 테이블명을 일일이 지정하기 어렵다면 그냥 VACUUM;을 실행해서 DB 전체를 미리 정리해 두는 것이 제일 속 편합니다.
  • VACUUM FULL은 DB를 잠그고 처음부터 다시 복사하므로 절대 함부로 실행하면 안 됩니다.
